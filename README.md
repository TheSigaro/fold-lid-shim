# FoldLidShim

Костыль для Galaxy Z Fold7, Android 16, без root. Служба читает угол через `AngleSource` (по умолчанию `hinge`) и в режиме Shizuku сверяет желаемое состояние с базовым состоянием Холла. Доступ к Samsung Folding Angle и Accelerometer-Sub закрыт разрешением `com.samsung.permission.SSENSOR` уровня signature|privileged. Приложение, shell и Shizuku получить его не могут.

## Режим без Shizuku

Выберите direct в карточке «Настройки», разрешите показ поверх других приложений, нажмите «Включить в настройках» и включите «FoldLidShim - подтверждение экрана» в специальных возможностях Android. Вернитесь в приложение: статус должен быть «Автоподтверждение: включено». Включите службу FoldLidShim. Shizuku, adb и Wi-Fi для этого режима не нужны.

StateActivity получает foreground-контекст для CLOSED и снятия запроса. Запрос OPENED приложению недоступен и из прямого пути удалён. Все запросы CLOSED используют только `setFlags(0)`: флаги 1 и 8 запрещены из-за ошибки Samsung в `setBaseState`. Поэтому приложение само снимает override; смена базового состояния его не отменяет.

| Желаемое | Наш CLOSED активен, включая ожидающий диалога | Текущее состояние | Действие |
| --- | --- | --- | --- |
| Закрыто | да | любое | NONE |
| Закрыто | нет | 0 | NONE |
| Закрыто | нет | 1, 2, 3, 4, 5, неизвестно | CLOSED |
| Открыто | да | любое | CANCEL |
| Открыто | нет | любое, включая 0, 4, 5 | NONE |

Исключение при старте: если состояние 0, своего запроса нет и hinge не ниже порога раскрытия, StateActivity один раз пробует снять оставшийся sticky-запрос погибшего процесса. Если система отказывает, ошибка остаётся в статусе. Чужие состояния 4/5 не оспариваются. Текущее состояние приходит из DeviceStateCallback, без dumpsys; диагноз Холла здесь использует доступное текущее состояние без нашего запроса, а не базовое.

На первом событии не выше порога закрытия (10° по умолчанию) CLOSED отправляется сразу. Нет прогрева по трём событиям, удержания, ожидания базового состояния или стабилизации. Настройка «Ранний запрос при складывании» включена по умолчанию: на угле <=45° и скорости уменьшения >=90°/с между соседними SensorEvent.timestamp запрос уходит раньше. Интервал должен быть положительным и не больше 500 мс, иначе скорость не используется. Угол раннего запроса настраивается в UI (15-90°, не ниже порога закрытия). Раннее CLOSED сохраняется при дальнейшем уменьшении угла; первое увеличение угла до/выше порога раскрытия (15° по умолчанию) немедленно снимает его. Это необходимо, чтобы следующие нисходящие отсчёты 40°, 30° не отменяли ранний запрос. Остановка на 70-120° не запрашивает CLOSED.

После исключения CLOSED не повторяется до смены желаемого состояния. Снятие своего запроса, напротив, повторяется с интервалом не меньше секунды до onRequestCanceled, пока угол в зоне раскрытия. Возврат ниже порога останавливает повторы. Binder-возврат cancel сам по себе не очищает владение. Выключение службы и смена режима сначала отменяют запрос через StateActivity и ждут подтверждения. При отказе служба остаётся для повторов и показывает ошибку. «Открыть принудительно» и плитка в direct только снимают запрос; ручное снятие подавляет автоматическое повторное закрытие до смены направления.

Если после ручного снятия остаётся 0 или диагноз STUCK_CLOSED, статус: «Система не даёт приложению запросить открытие. При залипании «закрыто» нужен Shizuku». При STUCK_CLOSED автоматических запросов нет. Настройка принудительного OPENED относится только к Shizuku.

Два старта с null intent за 10 минут выключают enabled и устанавливают статус «Служба выключена после аварийных перезапусков системы». Времена сохраняются в приватных настройках между процессами, ручное включение очищает предохранитель. Повторный boot/start без ручного включения его не снимает.

StateActivity использует общую задачу приложения, singleTop, FLAG_ACTIVITY_NO_ANIMATION, excludeFromRecents, noHistory, прозрачную тему без window-анимаций и preview. setShowWhenLocked(true) и setTurnScreenOn(true) включены; работа при блокировке без устройства не проверена.

Автоподтверждение ограничено com.android.systemui и нашим ожидающим запросом. Заголовок определяется по viewId `com.android.systemui:id/rear_display_title_text_view`, прежнему классу или русскому/английскому тексту. Основная кнопка ищется по `android:id/button1`; при отсутствии ID применяется последний непустой текст кнопки, кроме «Отмена» / «Cancel». После одного диагностического лога дерева распознанного rear-display диалога основной путь использует поиск по ID без обхода дерева. Остальные окна не логируются. Защита от повторного клика действует по паре (поколение запроса, windowId), без общей паузы между разными запросами.

## Журнал событий

Кнопка «Журнал» показывает последние записи приватного `files/timeline.log`. Ограничение файла 65536 байт; при заполнении старые полные строки отбрасываются, сохраняются последние примерно 32 КБ, новые записи добавляются в конец. Порядок хронологический, UTF-8. Формат строки:

```text
<unix-ms> elapsedNs=<монотонное-время> <событие и поля>
```

Для датчика дополнительно пишутся timestampNs из SensorEvent, receivedNs на входе обработчика и angle. Датчик логируется только при смене желаемого состояния или пересечении close/open/early, маска zone: бит 1 - <=close, бит 2 - >=open, бит 4 - <=early. Есть решения CLOSED/CANCEL, startActivity, onCreate, фокус, отправка request/cancel, activated/suspended/canceled, исключения, обнаружение диалога и клик, DeviceStateCallback, создание/перезапуск службы и предохранитель. Эти же ключевые события остаются в logcat.

Запись идёт вне пути запроса, одним временным IO-потоком, который завершается после 5 секунд простоя. Очередь ограничена 64 записями; при экстремальном переполнении новые записи могут быть отброшены. При внезапной смерти процесса последние ещё не записанные события могут потеряться.

```sh
adb shell run-as dev.pavlov.foldlidshim cat files/timeline.log
adb logcat -s FoldLidShim
```

run-as требует debuggable APK, например assembleDebug.

## Магнитометр

«Магнитометр» и «Экономия датчиков» включены по умолчанию. Используются первые три
значения `TYPE_MAGNETIC_FIELD_UNCALIBRATED` и `TYPE_GYROSCOPE`, оба non-wakeup,
период 10000 мкс, пакетирование 0. Системные bias v3..v5 не используются. Регистрация,
расчёты и калибровка выполняются на HandlerThread службы. Новых разрешений и wake lock нет.

С экономией датчики работают при `PowerManager.isInteractive`, независимо от hinge.
`ACTION_SCREEN_ON/OFF` вызывают повторную проверку на том же HandlerThread. При погашенном
экране подписки снимаются и окно очищается, при включении экранов начинается новое окно.
Без экономии датчики работают всё время службы. `interrupt_gyro` для управления питанием
больше не нужен. В строке статуса указана причина: экран включён, экран погашен,
без экономии или магнитометр отключён; отдельно показываются ошибки регистрации.
Закрытый телефон с включённым внешним экраном продолжает собирать историю для раскрытия.

`MagnetFoldDetector` сравнивает поле сейчас и ближайший отсчёт не позже 150 мс назад.
Из обоих вычитается H=(67.0,-30.7,11.9), старый вектор протягивается гироскопом по
`dE/dt = -omega x E`, поворотом Rodrigues. Направление M=(62,-25,1)/|M|.
Проекция разности s сравнивается с порогами +20 (closing) и -18 (opening) мкТл. Параметры находятся в `MagnetParams`.

Проверки правдоподобия:

- Поперечная составляющая разности не превышает 0.65*|s|, угол к соответствующему
  +M или -M не превышает 33.02 градуса. Для обоих направлений действует одно правило.
- Если |B-H| > R+|m0|+допуск = 42+67+20 = 129 мкТл, поле заведомо выходит за
  физическую оболочку даже закрытого телефона. Магнитные события и сбор калибровки
  запрещаются до 30 с после последнего такого отсчёта. Удаление чужого магнита тоже
  может выглядеть как настоящее раскрытие, поэтому проверять только текущую разность
  недостаточно. На записи 1 максимум |B-H|=100.23, этот запрет не включается.
  На записи 2 первое превышение в +56.283 с, до ложного события +56.403 с.

- Фантомное смыкание: если hinge 0 уже не меньше 700 мс и opening ещё не выдан,
  `s >= closeThreshold` продлевает карантин обеих сторон до 500 мс после отсчёта
  (`phantomHoldNs`). Проверка идёт до запретов preview и внешнего поля, без фильтра
  направления и проверки роста перед окном. Фантом внутри карантина продлевает его.
  Карантин сильного поля на 30 с не сокращается. Отрицательного аналога при hinge 180 нет.
- Для opening опорное поле B(t-W) сравнивается с отсчётом не позже чем на 300 мс
  раньше него (`preWindowNs`), повёрнутым гироскопом в кадр опоры тем же Rodrigues.
  Рост проекции на M больше 10 мкТл (`preRiseTolerance`) запрещает только текущего
  кандидата, без карантина. Падение любого размера допустимо. Без старой опоры
  opening запрещён. Оба буфера удерживают минимум W+preWindowNs+gapNs = 650 мс.
- Неподвижный телефон: только для opening максимум нормы гироскопа в замкнутом
  окне [t-W, t] сравнивается с `quietGyro=0.5` рад/с. Если отсчёты есть и максимум
  строго меньше 0.5, применяется `quietOpenThreshold=35` мкТл. Иначе, в том числе
  без гироскопа в окне, остаётся обычный порог opening. Closing не меняется.

Строгий тест состояния до/после по сферам |B-H|=42 и |B-H-67M|=42 с допуском
15..20 мкТл НЕ включён. Он не разделяет записи: у настоящего opening +12.951 с
закрытый радиус до события 75.74, ошибка +33.74; у closing +37.961 с открытый радиус
до 75.07, закрытый после 95.57, ошибки +33.07/+53.57. У ложного падения поля +59.893 с
закрытый радиус до 33.5, открытый после 25.1: оба проходят допуск 20. Более широкий
допуск не исправляет разделение. Ограничение 129 и выдержка после возмущения являются
более слабой проверкой состояния, а не подтверждением правильности двух сфер.
Чужое поле, которое остаётся внутри оболочки и повторяет движение магнита крышки,
в общем случае неотличимо; трёх записей недостаточно для гарантии на любом магните.

Closing разрешён при hinge <=90 не более 10 с после hinge 90, если после последнего
hinge 0 был hinge 180. Это блокирует отскок поля сразу после раскрытия. Opening разрешён
при hinge 0 не раньше 700 мс после смыкания. Защёлки подавляют повторы. Разрыв магнитометра
более 200 мс очищает оба окна. Неупорядоченные и более чем на секунду устаревшие события
игнорируются. Исключение: первый кэшированный hinge задаёт начальное состояние даже
со старым timestamp, что существенно для записи 2. Если гироскопа нет, используется
единичный поворот. Служба отклоняет кандидатов старше секунды относительно получения
и кандидатов, которых уже обогнал hinge.

`MagnetPreview` хранит предварительное желание; реальные углы продолжают поступать в
`DirectMotion.angle`. Предварительный угол 0/90 вычисляется через `previewAngle` с теми же
пользовательскими порогами, не меняя историю скорости. В direct opening означает
снятие собственного CLOSED, без своего запроса ничего не отправляется. HALF_OPENED
и OPENED прямой путь не запрашивает. Legacy Shizuku использует прежний `FoldDecider`.
Подтверждение hinge пишет `confirmed leadMs=...`. Сторож opening ждёт 800 мс,
closing 1500 мс, затем возвращает политику реального hinge и запрещает магнитные события
на 30 с. При откате сбрасываются didOpen/didClose и восстанавливается право на closing
из настоящего hinge-цикла. Hinge 180 немедленно отвергает предварительный closing.
Reload и выключение функции сбрасывают предварительность. В UI и Timeline остаются
последнее событие, опережение, ложные события и калибровка.

### v13: движение закрытого телефона у ноутбука

Три правила дополняют ограничения v12, без подбора выдержки под записи:

1. Рост перед окном: опора B(t-W) сравнивается с отсчётом за `preWindowNs=300` мс
   до неё с компенсацией гироскопом. Рост больше `preRiseTolerance=10` мкТл запрещает
   opening. Без старой опоры opening тоже запрещён.
2. Фантом: `openingReady && !didOpen && s >= closeThreshold` продлевает карантин
   до `phantomHoldNs=500` мс после текущего отсчёта. Проверки роста перед окном нет.
   Правило гасит пару «рост, затем спад» от чужого короткого импульса. За счёт окна
   150 мс положительный скачок может продлевать карантин ещё почти 150 мс.
3. Неподвижный телефон: при наличии гироскопа в [t-W, t] и max |ω| < `quietGyro=0.5`
   рад/с opening требует падения не меньше `quietOpenThreshold=35` мкТл. При движении
   или отсутствии отсчётов в окне действует обычный порог 18 мкТл (в sweep соответствующий T).
   Closing не меняется. Перемещение закрытого телефона в градиенте чужого поля
   может уменьшить проекцию без заметного вращения половины с датчиками.

## Запись датчиков

Нажмите «Запись датчиков», затем сверните приложение и несколько раз закройте и раскройте
телефон. Кнопка «Метка» добавляет якорь в запись. Кнопка «Стоп, осталось N с» останавливает
запись вручную; автоматически она заканчивается через 90 секунд или при достижении 30 МБ.
После остановки под кнопками показаны размер файла, число и типы зарегистрированных датчиков,
а также ошибки регистрации. Новый старт заменяет предыдущий `files/sensors.csv`.

Запись использует отдельную foreground-службу и временный partial wake lock, чтобы непрерывные
датчики работали после ухода из UI. Она не включает службу складывания и не запускает Shizuku.
Все слушатели записи, поток, wake lock и её служба освобождаются при остановке. При убийстве
процесса запись не возобновляется, последние буферизованные строки могут потеряться.

Для debug APK заберите файл и запустите анализ на компьютере с Python 3.10+:

```sh
adb shell run-as dev.pavlov.foldlidshim cat files/sensors.csv > sensors.csv
python3 tools/sensors_report.py sensors.csv
python3 tools/sensors_report.py sensors.csv --anchor-threshold 6 --window-ms 1000 --step-ms 50
```

Формат UTF-8 CSV с разделителем `;` и десятичной точкой:
`elapsedNs;timestampNs;type;name;v0;v1;v2;...`. Сохраняются все значения, включая поправки
некалиброванных датчиков. Текстовые поля с разделителем, кавычкой или переводом строки
экранируются по правилам CSV. Первая строка: `elapsedNs;0;header;<unix-ms старта>;<Build.MODEL>`.
Состояния и метки: `elapsedNs;0;state;<committed state>` и `elapsedNs;0;mark;<текст>`.

Скрипт показывает число событий и средний период каждого датчика, изменения hinge_angle,
состояния, метки и всплески ускорения. Время датчиков берётся из `SensorEvent.timestamp`,
время состояний и меток - из `elapsedRealtimeNanos` при получении. Ноль относительного времени
соответствует заголовку. Окно вокруг якоря содержит последние отсчёты не позже каждой точки;
`n/a` означает отсутствие предыдущего отсчёта. Модули векторов используют первые три значения.
Магнитное поле измеряется в мкТл, ускорение в м/с², гироскоп в рад/с; скалярные значения
сохраняют единицы датчика. Статистика магнитометра включает модуль и оси x/y/z.

Отбирается один экземпляр каждого типа без requiredPermission, только continuous и on-change,
с предпочтением первого non-wake-up. По известному списку Fold7 ожидается 21 тип:
accelerometer (1), gyroscope (4), accelerometer_uncalibrated (35), gyroscope_uncalibrated (16),
magnetic_field (2), magnetic_field_uncalibrated (14), gravity (9), linear_acceleration (10),
rotation_vector (11), game_rotation_vector (15), orientation (3), pressure (6), light_ir,
light_cct, hinge_angle (36), light (5), proximity (8), device_orientation (27), interrupt_gyro,
device_common_info и Motion Sensor (65559). Числовые типы vendor-датчиков видны в UI и файле.
Фактическая регистрация зависит от SensorManager; датчики с SSENSOR не запрашиваются.

## Расход ресурсов

В direct нет ShizukuAutoStarter, сетевого callback автозапуска, его executor, reconcileTick и периодического чтения состояния. При переходе из Shizuku в direct прежнее соединение освобождается, поздний binder callback не биндит заново. ShizukuAutoStarter, adb, BinderNudgeActivity и ReconcilePolicy не изменены. Процесс :nudge по-прежнему используется только существующим автозапуском.

В покое остаются основной Android looper, один спящий HandlerThread службы, on-change hinge listener, DeviceStateCallback на main executor и listener ShimState службы. При стандартном hinge нет второй подписки на тот же датчик. Для альтернативного источника hinge нужен отдельно для диагностики. Wake lock в direct не создаётся и не берётся. Фоновый постоянный executor DeviceStateManager заменён исполнением callback на main.

Периодических таймеров в обычном покое нет. Условные одноразовые задачи: таймаут StateActivity/службы 3 секунды, таймаут подтверждения 5 секунд в контроллере, повтор cancel раз в секунду только до подтверждения и при раскрытии/остановке/смене режима. Они не задерживают отправку команды. IO worker журнала существует максимум 5 секунд после записи. Таймер UI 200 мс и диагностические датчики живут только при раскрытой карточке «Датчики» и resumed-активити. UI снимает ShimState и bridge listeners в onStop, StateActivity снимает listener в onDestroy. Тестовая кнопка явно планирует снятие через 3 секунды, даже если UI успеет уйти в фон; это однократное завершение ручного теста. Executor плитки создаёт поток только для Shizuku и закрывается в onDestroy.

```sh
adb shell dumpsys batterystats --charged dev.pavlov.foldlidshim
adb shell dumpsys meminfo dev.pavlov.foldlidshim
adb shell dumpsys procstats --hours 3 dev.pavlov.foldlidshim
```

Смотреть частоту wakeups, partial wakelocks, работу сенсоров и CPU в batterystats; total PSS, Java/native heap и число потоков в meminfo; длительность foreground/service и min/avg/max PSS/USS в procstats. Сравнивать одинаковые интервалы простоя/складываний после зарядки. Численных результатов без телефона нет.

## Ключ adb с компьютера

Основной путь - один раз импортировать ключ ноутбука, который уже авторизован на этом телефоне через USB с опцией «Всегда разрешать»:

```sh
adb push ~/.android/adbkey /sdcard/Download/adbkey
```

В карточке Shizuku нажмите «Импортировать ключ adb», выберите файл `adbkey`. Поддерживается PEM `BEGIN PRIVATE KEY`, PKCS#8, RSA 2048. PKCS#1 `BEGIN RSA PRIVATE KEY`, другие размеры и мусор отклоняются с сообщением «Это не ключ adb». Файл остаётся в Download - после импорта удалите его вручную. Затем выполните:

```sh
adb shell pm grant dev.pavlov.foldlidshim android.permission.WRITE_SECURE_SETTINGS
```

Ключ и флаги `adb_key_paired=true`, `adb_key_imported=true` сохраняются одним commit через `PreferenceAdbKeyStore` в приватном device-protected хранилище `adb_identity`. Резервное копирование выключено. Статус ключа: «нет», «импортирован», «сопряжён». Старый ключ без `adb_key_paired=true` считается несопряжённым: «нет (нужен импорт)», автозапуск его не использует.

Запасной путь - «Сопряжение adb». Откройте этот экран в split-screen вместе с Настройками. В Настройках включите беспроводную отладку и откройте диалог кода. Введите шесть цифр в поле приложения и нажмите «Связать». Настройки должны оставаться resumed: уход в фон закрывает сервер `_adb-tls-pairing._tcp`. Оверлей удалён. Новый ключ готовится в памяти для протокола, в настройки попадает только после успешного сопряжения. Неудачная попытка не заменяет сохранённый ключ.

## Запуск и автозапуск Shizuku

1. Установите Shizuku (`moe.shizuku.privileged.api`) и приложение.
2. Импортируйте авторизованный ключ и выдайте WRITE_SECURE_SETTINGS по инструкции выше.
3. Подключитесь к Wi-Fi. Кнопка «Запустить Shizuku» открывает Shizuku, «Запустить автоматически» запускает существующий автозапуск v5.
4. Когда Shizuku работает, нажмите «Выдать разрешение» и подтвердите доступ приложения.
5. Включите службу. При необходимости отключите оптимизацию батареи.

Автозапуск проверяет binder. Если Shizuku доступен, пишет «Shizuku уже работает». Иначе включает `adb_wifi_enabled`, ищет локальный `_adb-tls-connect._tcp`, подключается по TLS с сохранённым ключом и запускает невидимую активити для запроса binder, ожидая до 3 секунд. Если binder не получен, запускает starter установленного Shizuku, затем до трёх раз с паузой 1,5 с снова запускает невидимую активити и ждёт binder, всего до 10 секунд. Shizuku отдаёт binder только при появлении нового процесса или смене состояния процесса, поэтому активити живёт в отдельном процессе `:nudge` и завершает его сразу после работы. При отсутствии порта выполняется переключение беспроводной отладки. После успеха настройка «Выключать беспроводную отладку после запуска» выключает её (включена по умолчанию).

Повторы после ошибок: 10, 20, 40, 60 секунд, далее по 60 секунд, окно 30 минут. Событие Wi-Fi вызывает попытку сразу, одновременно работает одна попытка. Без ключа или WRITE_SECURE_SETTINGS причина показывается в карточке Shizuku. Последняя попытка содержит время, этап и ошибку. Если служба включена, BOOT_COMPLETED запускает её после перезагрузки; LOCKED_BOOT_COMPLETED не используется.

## Диагноз Холла и что делает костыль

`HallDiagnosis` хранит историю только за текущую сессию службы: минимум и максимум настоящего hinge, последний угол, изменения базового состояния. Override не считается изменением Холла. Hinge наблюдается отдельно от выбранного управляющего источника.

- «работает»: базовое состояние менялось и сейчас согласуется с углом (0 в закрытой зоне, 2/3 в открытой). Совпавший override снимается.
- «залип открыто»: базовое всегда 2/3, hinge менялся. Закрытие запрашивается по углу, при раскрытии возвращается базовое открытое состояние.
- «залип закрыто»: базовое всё время 0, получен hinge 0.0 и максимальный угол сессии остался 0.0, прошло хотя бы 60 секунд. Служба не отправляет команды по углу. Используйте ручные кнопки или плитку.
- «пока неясно»: данных недостаточно или они не согласуются. Отсутствие событий hinge не приравнивается к нулевому углу.

В Shizuku диагноз пересчитывается при событиях выбранного источника и при 30-секундном опросе, поэтому отсутствие новых событий нулевого hinge не мешает выдержке 60 секунд. История сохраняется до остановки службы, при восстановлении Холла диагноз может перейти в «работает» без перезапуска.

Перед автоматическим изменением состояния в Shizuku читается сырой `dumpsys device_state`, который разбирает чистый `DeviceStateInfo`. Базовое состояние отделено от `mOverrideState` и `Override Request active`. `ReconcilePolicy` выбирает команду:

| Желаемое состояние | Базовое состояние | Наш override активен | Команда |
| --- | --- | --- | --- |
| CLOSED | 0 | да | reset |
| CLOSED | 0 | нет | ничего |
| CLOSED | 1, 2, 3, 4, 5 | любое | state 0 |
| OPENED | 2, 3 | да | reset |
| OPENED | 2, 3 | нет | ничего |
| OPENED | 0, 1, 4, 5 | любое | state 3 |
| CLOSED / OPENED | чтение не удалось | любое | state 0 / state 3 по углу |

Таблица для включённого «Принудительное OPENED при раскрытии». Если настройка выключена, вместо `state 3` используется прежний `reset`. Чужой override не снимается только потому, что базовое состояние совпало: нужна локальная отметка об успешно отправленной нашей команде и активный override в dumpsys. Если override исчез или его состояние отличается от нашего запроса, локальное владение сбрасывается.

В `FoldService.reconcileTick` на рабочем Handler раз в 30 секунд перечитывается состояние. `ShizukuBridge.releaseMatchingOverride` снимает только совпавший наш override командой `reset`. Таймер не повторяет `state 0/3`. Служба, плитка и кнопки используют общий сериализованный ShizukuBridge и общий учёт желаемого состояния, поэтому ручной запрос также участвует в сверке. Системное текущее состояние для плитки читается через `cmd device_state print-state`.

В Shizuku угол <= 10 градусов по умолчанию закрывает без выдержки, >= 15 раскрывает, между порогами действует гистерезис. Пороги валидируются: `0 <= закрыто < открыто <= 180`, конечные значения. `StartupGate` по-прежнему ждёт три корректных события управляющего источника; `FoldDecider` подавляет повторы, обрабатывает удержание, ошибки и смену направления. Смена источника сбрасывает прогрев, но не историю Холла.

## Плитка

Добавьте «Экран Fold» через редактирование быстрых настроек. Тап отправляет через Shizuku `state 3`, если текущее состояние 0, иначе `state 0`. Подпись показывает текущее состояние, при неготовом Shizuku плитка недоступна. В direct плитка использует текущее состояние DeviceStateCallback и запускает StateActivity только для снятия запроса. Плитка работает и без запущенной службы. При STUCK_CLOSED автоматические команды службы отключены, поэтому ручное раскрытие не отменяется нулевым углом.

Те же команды доступны кнопками «Открыть принудительно» и «Закрыть принудительно» в карточке «Ручное управление». «Проверить сейчас» сохранилась: закрытие и через три секунды раскрытие по настройке. Это явная ручная проверка.

## Главный экран

Тема `Theme.Material3.DayNight.NoActionBar` поддерживает светлый и тёмный режимы. Карточки с закруглением и отступами 16 dp расположены так:

1. Статус: крупное состояние телефона, угол, диагноз Холла, действие костыля, переключатель службы справа.
2. Shizuku: статус, разрешение только при необходимости, открытие Shizuku, импорт ключа, автозапуск и запасное сопряжение.
3. Ручное управление: принудительные состояния, подсказка о плитке, проверка.
4. Настройки: shizuku/direct с предупреждением, источник, пороги, принудительное OPENED, отключение беспроводной отладки.
5. Датчики: свёрнута по умолчанию, раскрывается по тапу, сырые значения и инверсия осей sub.
6. Шторка уведомлений: пояснение и переход в настройки уведомлений Shizuku.

Источники `samsung`, `accel`, `hinge` и direct сохранены. В direct используются `DirectStateController`, `StateActivity` и автоподтверждение через службу специальных возможностей; см. «Режим без Shizuku». Недоступный выбранный источник не заменяется автоматически. Для accel сохранены инверсия осей и среднее последних пяти пересчётов. Диагностические датчики работают только при раскрытой карточке и resumed-активити, обновление 200 мс.

## Как убрать уведомления из шторки

Приложение не объявляет и не запрашивает POST_NOTIFICATIONS. Обязательное foreground-уведомление создаётся до работы службы на канале IMPORTANCE_MIN, с `setSilent(true)`, без `FOREGROUND_SERVICE_IMMEDIATE`. Отозванное разрешение не является условием запуска службы: `startForeground` вызывается независимо от него. Android требует small icon для foreground-уведомления; убрать её полностью через публичный API нельзя, видимость ограничивается каналом и системным разрешением. Android может показывать службу в системном списке активных приложений.

Уведомление «Shizuku работает» принадлежит другому пакету. Кнопка «Скрыть уведомление Shizuku» открывает `Settings.ACTION_APP_NOTIFICATION_SETTINGS` с `EXTRA_APP_PACKAGE=moe.shizuku.privileged.api`. Отключите уведомления там вручную.

## Проверки и сборка

```sh
./gradlew --no-daemon testDebugUnitTest lintDebug assembleDebug
shellcheck build.sh
```

JUnit: `ConfirmButtonPickerTest` (русские и английские подписи, отсутствие rear display, только отмена, wrapper, пустые кнопки), `DirectPolicyTest` (все ветки выбора команд), `DeviceStateInfoTest`, `ReconcilePolicyTest`, `HallDiagnosisTest`, `AdbCommandsTest`, а также существующие тесты FoldDecider, StartupGate, порогов, углов, adb-протокола и повторов. Нужны Android SDK 36, JDK 17, NDK 28.0.13004108, CMake 3.22.1. Docker-образ содержит NDK и CMake. `./build.sh` собирает через Docker APK в `out/app-debug.apk`.

APK ставить (`adb install -r out/app-debug.apk`) только на раскрытом телефоне, когда у службы нет активного запроса CLOSED: `adb shell dumpsys device_state | grep 'Override Request active'` должен показать `false`. Установка убивает процесс, а его запрос остаётся активным от мёртвого pid: новый процесс снять его не может, телефон залипает в CLOSED с выключенным внутренним экраном, в журнале только `device state=0`. Как снять такой запрос, написано в разделе «Остановка и логи». После установки службу поднимает `BootReceiver` по `MY_PACKAGE_REPLACED`, если переключатель был включён; служба спецвозможностей перепривязывается системой сама.

## Остановка и логи

Выключение службы снимает её override. Если процесс был убит (например, установкой APK на закрытом телефоне), запрос остаётся активным от мёртвого pid, и новый процесс снять его не может. `adb shell cmd device_state state reset` тут не помогает: он снимает только запрос самой оболочки. Снять чужой запрос без перезагрузки: `adb shell cmd device_state state 3` (запрос оболочки вытесняет застрявший), затем `adb shell cmd device_state state reset` возвращает физическое состояние; если телефон закрыт, служба через полсекунды сама запрашивает CLOSED заново. Проверка: в `adb shell dumpsys device_state` строка `Override Request active: false` или `Request: mPid=` с pid живого процесса. Логи: `adb logcat -s FoldLidShim`.
