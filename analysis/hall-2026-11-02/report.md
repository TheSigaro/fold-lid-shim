Реплей сохраняет порядок CSV, защитные условия и временные метки событий. Это решения детектора и простого hinge-правила 10/15, а не полная эмуляция службы: экранные broadcasts, preview watchdog, rollback, bounce, binder и пользовательские настройки не записаны. ## Все callback состояния

В ячейках сенсоров: значение (Δ мс). Input: угол/state (Δ). B2/B14/score: мкТл (возраст последнего отсчёта, Δ). P: строка политики (lastState -> newState, Δ) в пределах 1.5 с; для раскрытий ищется выход политики из 0, который может дать 1 при callback=2. Для угловых переходов сначала ищется тот же from/to, затем тот же newState, включая повторное решение. U: ближайший lid-switch update с нужным foldOpen в пределах 1.5 с, W: ближайший wake в пределах 1.5 с, только для переходов Холла. Соседние fusion могут принадлежать другому циклу: датчик отключается в закрытом состоянии.

## Выводы и рекомендуемые настройки

Hinge: DEFAULT_CLOSE_DEG=10 и DEFAULT_OPEN_DEG=15 не менять. Любые C в [0,90) и O в (0,90] дают те же решения на 0/90/180, поэтому настройкой этих порогов время переключения исправить нельзя. По таблице реплея в 3 из 8 закрытий hinge0 опережает Холл на 134.417 / 381.238 / 622.261 мс (min/median/max), по receivedNs опережение составляет 133.401 / 380.267 / 621.316 мс. Для evaluateDirect это означает, что правило угла уже запрашивает CLOSED при ещё открытом по Холлу телефоне: возможен преждевременный перевод экранов. Это вывод для правила без остальных блокировок службы. В остальных найденных закрытиях Δ hinge0 равна 3.611 / 55.806 / 161.021 мс. Перенос порога закрытия на 90 только приблизит преждевременное закрытие, включая остановки в полураскрытом положении. Фиксированную задержку по этой записи также не рекомендовать: знак и величина ошибки зависят от движения. Точнее повторить Холл можно только с дополнительным сигналом или изменением логики подтверждения, что выходит за настройку порогов. Код приложения не менять.

Магнитометр: при текущих C/O=20/18 пропущено 4 из 8 закрытий. В 3 пропусках после полного раскрытия hinge0 приходит раньше Холла и сбрасывает openedSinceClosed до достаточного магнитного импульса; ещё в 1 случаях после предыдущего раскрытия нет hinge180, поэтому closing запрещён. В диагностике выбранных максимумов score блокировка no hinge180 указана в 4 строках, недостижение порога - в 2. Как оговорено у таблицы диагностики, это причины для выбранного отсчёта, а не доказательство блокировки каждого отсчёта окна.
Лучший по критерию покрытия и отставания вариант проверенной сетки C/O=9/9, hold=10 с находит 16/17 событий без лишних по правилу сопоставления. Но 7 закрытий происходят РАНЬШЕ Холла на 138.401 / 176.213 / 694.282 мс (min/median/max). В приложении это означает преждевременный запрос CLOSED и переключение экранов до физического срабатывания Холла. Отсутствие лишних пар в окне +/-1.5 с не означает совпадение момента переключения. Конкретная рекомендация: не заменять рабочие 20/18 на этот вариант ради имитации Холла. Использовать его только как экспериментальный кандидат для следующей записи. Оставить 20/18, quiet-open=35, phantom-hold=500 мс и foreign-field hold=10 с до проверки подтверждения закрытия и отрицательных контрольных записей. При этом 20/18 не объявляются решением пропущенных закрытий: их ограничения требуют отдельной проверки логики gate, а не только снижения порога.

### 4. Стоят ли строки обработки SW_LID раньше newState?

Нет, позже: update на 0.041 / 0.075 / 2.870 мс, wake на 1.821 / 171.950 / 967.929 мс (min/median/max). Сопоставлено update: 17, wake: 8. Это порядок диагностических строк, а не физических событий. Wake выбран в пределах 1.5 с и может относиться к следующему угловому решению; отсутствие строки не заменяется нулевой задержкой.

### 5. Чего не хватает для надёжных выводов?

Запись длится 55.599 с, начинается уже CLOSED; измерено 8 закрытий и 9 раскрытий. Есть пакетная доставка hinge и задержка callback. Неизвестны точные физические времена Холла, настройки службы, сохранённая калибровка, истинный непрерывный угол и пользовательские метки темпа. Медленных движений с длинной остановкой у порога и отрицательных контрольных сценариев недостаточно для надёжной настройки. Нужны несколько повторов по 20-30 циклов: отдельно медленно у 0-30 градусов, быстро, с паузами 5-15 с на 5/10/20/45/90 градусах, без полного раскрытия между циклами, в разных ориентациях. Добавить синхронные SW_LID/input-event timestamps, видео/непрерывный угол, метки действий, screen broadcasts и замеры задержки регистрации fusion. Для оценки ложных событий записать неподвижный закрытый телефон, перенос и вращение, посторонние магниты и зарядку без складываний. Приложение и существующий реплей не изменены.
