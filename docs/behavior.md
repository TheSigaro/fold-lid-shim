# Поведение службы

Костыль для Galaxy Z Fold7, Android 16, без root. Служба читает угол через `AngleSource` (по умолчанию `hinge`) и запрашивает CLOSED при складывании, а при раскрытии снимает свой запрос. Доступ к Samsung Folding Angle и Accelerometer-Sub закрыт разрешением `com.samsung.permission.SSENSOR` уровня signature|privileged. Приложение и shell получить его не могут.


## Как работает переключение

Разрешите показ поверх других приложений, нажмите «Включить в настройках» и включите «FoldLidShim - подтверждение экрана» в специальных возможностях Android. Вернитесь в приложение: статус должен быть «Автоподтверждение: включено». Включите службу FoldLidShim.

StateActivity получает foreground-контекст для CLOSED (0), OPENED (3) и снятия запроса. Оба запроса используют только `REQUEST_FLAGS = 2`: штатный бит 2 прошивки Samsung сохраняет override при засыпании. Бит 1 запрещён из-за падения system_server; биты 8 и 16 не используются. Приложение само снимает запрос при смене направления.

| Желаемое | Свой запрос | Состояние без своего запроса | Действие |
| --- | --- | --- | --- |
| Закрыто | CLOSED | любое | NONE |
| Закрыто | OPENED | любое | CANCEL |
| Закрыто | нет | 0 | NONE, следует прошивке |
| Закрыто | нет | другое или неизвестно | CLOSED по свежему свидетельству, во сне после 1000 мс с повторной блокировкой |
| Открыто | CLOSED | любое | CANCEL, во сне только после подтверждения раскрытия |
| Открыто | OPENED | любое | NONE |
| Открыто | нет | 0 | После recovery и выдержки 700 мс запрос OPENED |
| Открыто | нет | другое или неизвестно | NONE, при переходе из закрытого во сне только WAKE |

Исключение при старте: если состояние 0, своего запроса нет и hinge не ниже порога раскрытия, StateActivity один раз пробует снять оставшийся sticky-запрос погибшего процесса. После результата этой попытки действует путь OPENED ниже. Чужие состояния 4/5 не оспариваются. Текущее и, если прошивка его сообщает, базовое состояние приходят из DeviceStateCallback, без dumpsys. Базовое состояние имеет приоритет над текущим состоянием без нашего запроса для решений и диагноза Холла.

При включённом экране на первом событии не выше порога закрытия (10° по умолчанию) CLOSED отправляется сразу. Нет прогрева по трём событиям, удержания, ожидания базового состояния или стабилизации. Настройка «Ранний запрос при складывании» включена по умолчанию: на угле <=45° и скорости уменьшения >=90°/с между соседними SensorEvent.timestamp запрос уходит раньше. Интервал должен быть положительным и не больше 500 мс, иначе скорость не используется. Угол раннего запроса настраивается в UI (15-90°, не ниже порога закрытия). Раннее CLOSED сохраняется при дальнейшем уменьшении угла; первое увеличение угла до/выше порога раскрытия (15° по умолчанию) снимает его с защитой от дребезга, описанной ниже. Это необходимо, чтобы следующие нисходящие отсчёты 40°, 30° не отменяли ранний запрос. Остановка на 70-120° не запрашивает CLOSED.

После исключения CLOSED не повторяется до смены желаемого состояния. Снятие своего запроса, напротив, повторяется с интервалом не меньше секунды до onRequestCanceled, пока угол в зоне раскрытия. Возврат ниже порога останавливает повторы. Binder-возврат cancel сам по себе не очищает владение. Выключение службы сначала отменяет запрос через StateActivity и ждёт подтверждения. При отказе служба остаётся для повторов и показывает ошибку. «Открыть принудительно» и плитка только снимают запрос; ручное снятие подавляет автоматическое повторное закрытие до смены направления.

Если после ручного снятия остаётся 0 при hinge в открытой зоне, служба использует путь OPENED ниже. Диагноз STUCK_CLOSED не блокирует команды.

Два старта с null intent за 10 минут выключают enabled и устанавливают статус «Служба выключена после аварийных перезапусков системы». Времена сохраняются в приватных настройках между процессами, ручное включение очищает предохранитель. Повторный boot/start без ручного включения его не снимает.

StateActivity обрабатывает смену дисплея через `configChanges` (screenSize, smallestScreenSize, screenLayout, orientation, density, uiMode, keyboardHidden, keyboard, navigation) без пересоздания и пишет `StateActivity config changed`. Одноразовое действие по фокусу и его дедлайн сохраняются. StateActivity использует общую задачу приложения, singleTop, FLAG_ACTIVITY_NO_ANIMATION, excludeFromRecents, noHistory, прозрачную тему без window-анимаций и preview. setShowWhenLocked(true) и setTurnScreenOn(true) включены; работа при блокировке без устройства не проверена.

Автоподтверждение ограничено com.android.systemui и нашим ожидающим запросом. Заголовок определяется по viewId `com.android.systemui:id/rear_display_title_text_view`, прежнему классу или русскому/английскому тексту. Основная кнопка ищется по `android:id/button1`; при отсутствии ID применяется последний непустой текст кнопки, кроме «Отмена» / «Cancel». После одного диагностического лога дерева распознанного rear-display диалога основной путь использует поиск по ID без обхода дерева. Остальные окна не логируются. Защита от повторного клика действует по паре (поколение запроса, windowId), без общей паузы между разными запросами.

### Сон закрытого телефона

Основной путь: флаг 2 сохраняет CLOSED при засыпании. Телефон спит в состоянии 0,
callback снятия не приходит, служба ничего не делает. Тапы по внешнему экрану и AOD
работают штатно. Кнопка питания будит закрытый телефон без нового запроса или диалога.

При складывании спящего телефона, если своего запроса нет и система ещё не CLOSED,
служба ждёт 1000 мс (`ASLEEP_CLOSED_GRACE_MS`) и один раз пишет
`closed while asleep: waiting for system`. Одноразовый таймер проверяет решение в конце
выдержки. Если система за это время сама сообщила 0, пишется
`system already CLOSED, no request`, activity не запускается и приложение не будит телефон.
Раскрытие отменяет выдержку без отдельной записи. Если пользователь включил экран,
CLOSED запрашивается сразу, без повторной блокировки по этому правилу.
Если срок истёк, экран всё ещё погашен, система не в 0 и решение о закрытии свежее,
служба пишет `closed while asleep: request CLOSED` и запускает обычный ACTION_CLOSED.
StateActivity с turnScreenOn будит внутренний экран внутри закрытого телефона.
После onRequestActivated служба специальных возможностей один раз на запрос вызывает
`GLOBAL_ACTION_LOCK_SCREEN`: `relock after closed` при успехе или `lock unavailable`.
Если пользователь успел включить экран кнопкой питания, повторная блокировка всё равно
выполняется. Без доступной блокировки экран уснёт по штатному таймауту.
При включённом экране выдержки перед CLOSED нет.

Запасной путь v15: если прошивка всё же сняла CLOSED при `isInteractive=false`
или в пределах 1 секунды после `ACTION_SCREEN_OFF`, журнал содержит
`sleep cancel generation=N`. До пробуждения повторного запроса нет.
При `ACTION_SCREEN_ON` менее чем через 1,5 секунды после снятия журнал содержит
`sleep cancel: spurious wake after N ms, lock`, выполняется `GLOBAL_ACTION_LOCK_SCREEN`.
Если блокировка недоступна или не выполнена, пишется `lock unavailable`, новых запросов
нет, экран уснёт по таймауту. Нажатие кнопки в первые 1,5 секунды также может снова
заблокировать телефон; следующее нажатие после окна сработает.
Позднее пробуждение пишет `wake: request CLOSED` и запускает обычный запрос с диалогом,
если система сама ещё не CLOSED.

Во сне раскрытие принимается только после `magnet opening confirmed` или реального
отсчёта hinge не ниже порога раскрытия (15° по умолчанию). Угол 90° из ожидающего
магнитного события подтверждением не считается. До подтверждения один раз пишется
`opening unconfirmed: waiting`: свой CLOSED не снимается, ACTION_WAKE не запускается.
При `magnet opening false` никаких действий нет. Цена подтверждения по замеру
составляет примерно 250-500 мс после первого магнитного события; реальный hinge в
открытой зоне может разрешить действие раньше.
Подтверждённое раскрытие со своим CLOSED запускает ACTION_OPEN и снимает запрос:
переход 0 -> 2/3 включает внутренний экран. Без своего запроса переход желания
CLOSED -> OPEN пишет `wake on open`: ACTION_WAKE получает фокус и будит экран,
если прошивка ещё не увидела раскрытие и экран всё ещё погашен.
Начальный открытый угол при старте службы сам по себе экран не будит.
При включённом экране снятие CLOSED остаётся по первому, даже неподтверждённому событию.

### Когда датчик Холла работает

Если при закрытии базовое состояние (или текущее без собственного запроса при
отсутствии базового) уже 0, приложение пассивно: `system already CLOSED, no request`
пишется один раз на эпизод закрытия. При складывании во сне выдержка 1000 мс
даёт прошивке самой перейти в 0 без лишних запросов и пробуждений от приложения.
При уходе системы из 0 в 1, 2 или 3 без своего запроса пишется
`system left CLOSED, decision reset`, ожидающий ACTION_CLOSED сразу снимается.
Старое решение «закрыто» больше не создаёт CLOSED и повторную блокировку:
нужно новое магнитное событие closing или отсчёт hinge не выше порога закрытия,
полученные строго позже системного раскрытия. Липкое решение новым свидетельством
не считается. Приложение не запускает WAKE по такому раскрытию: прошивка будит
телефон сама. Правило действует и при включённом, и при погашенном экране,
без ожидания магнитометра или hinge. Если Холл ожил при своём активном CLOSED
и база стала 0, запрос сохраняется до раскрытия. Аналогично свой OPENED сохраняется
при базе 3 до складывания.

Любая отмена запроса принимает состояние из последнего callback за состояние
без запроса до следующего callback и пишет `request canceled before activation,
system state=N` или `request canceled after activation, system state=N`.
Неактивированный запрос (диалог не подтверждён, а крышка уже закрылась по Холлу)
система снимает без повторного callback: при 0 следующий запрос не отправляется,
а не повторяется каждую секунду. Активированный CLOSED система снимает, когда
база сама стала 0: callback `device state=0` приходит через 0,1-3 мс после
отмены, и без этой записи оценка между ними решала CLOSED и запускала лишнюю
StateActivity (при погашенном экране она будит его). Если база отличается от
последнего состояния, следующий callback поправит запись за миллисекунды.

### Залипание «закрыто»

При hinge >= порога раскрытия (15° по умолчанию), отсутствии своего запроса и
системном состоянии 0 служба ждёт `OPENED_GRACE_MS = 700` мс от первого такого
отсчёта. Выход из открытой зоны или системного 0 сбрасывает выдержку.
Одноразовая попытка recovery чужого sticky-запроса должна завершиться или быть
неприменима. Затем `lid stuck closed: request OPENED` запускает ACTION_OPENED
через StateActivity, запрашивающую состояние 3 с тем же флагом 2.
При onRequestActivated внутренний экран должен включиться; диалог Samsung для 3
не ожидается. При складывании свой OPENED снимается через ACTION_OPEN с теми же
повторами снятия раз в секунду до callback.

При исключении системы пишется `OPENED refused: <класс и сообщение>`, статус:
«Система отклонила запрос OPENED. Повтор после смены направления; для открытия доступен adb с компьютера».
Повторной попытки до следующей смены направления нет. Проверено на SM-F966B
(Android 16): OPENED без CONTROL_DEVICE_STATE прошивка отклоняет с
SecurityException и во сне под блокировкой, и при бодрствующем разблокированном
телефоне со StateActivity в фокусе; приложениям доступен только CLOSED (режим
заднего экрана). Залипание «закрыто» снимается только adb с компьютера:
`cmd device_state state 3`, потом `state reset`. При залипшем в «закрыто» Холле
`hinge_angle` всегда 0, поэтому по hinge путь OPENED и не запускается.

В первые 1,5 секунды после отправки CLOSED раскрытие только по hinge удерживается
300 мс. Возврат в закрытую зону за это время игнорирует дребезг и пишет
`hinge bounce ignored angle=90.0 afterMs=N`. Если новых отсчётов нет, одноразовый
таймер через 300 мс снимает запрос. При включённом экране магнитное раскрытие и раскрытие вне окна
1,5 секунды выполняются сразу. Во сне дополнительно требуется подтверждение раскрытия,
описанное выше.

## Журнал событий

Кнопка «Журнал» показывает последние записи приватного `files/timeline.log`. Ограничение файла 65536 байт; при заполнении старые полные строки отбрасываются, сохраняются последние примерно 32 КБ, новые записи добавляются в конец. Порядок хронологический, UTF-8. Формат строки:

```text
<unix-ms> elapsedNs=<монотонное-время> <событие и поля>
```

Для датчика дополнительно пишутся timestampNs из SensorEvent, receivedNs на входе обработчика и angle. Датчик логируется только при смене желаемого состояния или пересечении close/open/early, маска zone: бит 1 - <=close, бит 2 - >=open, бит 4 - <=early. Есть решения CLOSED/CANCEL, `lid stuck closed: request OPENED`, `system already CLOSED, no request`, `closed while asleep: waiting for system`, `closed while asleep: request CLOSED`, `opening unconfirmed: waiting`, `system left CLOSED, decision reset`, `relock after closed`, `lock unavailable`, `OPENED refused: <класс и сообщение>`, `base state=N`, `requestState send state=N generation=N flags=2`, startActivity, onCreate, фокус, отправка request/cancel, activated/suspended/canceled, исключения, обнаружение диалога и клик, DeviceStateCallback, создание/перезапуск службы и предохранитель. Эти же ключевые события остаются в logcat.

Запись идёт вне пути запроса, одним временным IO-потоком, который завершается после 5 секунд простоя. Очередь ограничена 64 записями; при экстремальном переполнении новые записи могут быть отброшены. При внезапной смерти процесса последние ещё не записанные события могут потеряться.

```sh
adb shell run-as dev.pavlov.foldlidshim cat files/timeline.log
adb logcat -s FoldLidShim
```

run-as требует debuggable APK, например assembleDebug.

## Расход ресурсов

В покое остаются основной Android looper, один спящий HandlerThread службы, on-change hinge listener, DeviceStateCallback на main executor и listener ShimState службы. При стандартном hinge нет второй подписки на тот же датчик. Для альтернативного источника hinge нужен отдельно для диагностики. Служба переключения не создаёт и не берёт wake lock. Фоновый постоянный executor DeviceStateManager заменён исполнением callback на main.

FoldService динамически принимает защищённые `ACTION_SCREEN_ON/OFF` на своём HandlerThread и снимает приёмник в onDestroy, независимо от настроек магнитометра. Периодических таймеров в обычном покое нет. Для дребезга добавлен одноразовый таймер 300 мс только при кандидате раскрытия в окне 1,5 секунды; политика сна сравнивает монотонные времена без периодического таймера. Условные одноразовые задачи: таймаут StateActivity/службы 3 секунды, таймаут подтверждения 5 секунд в контроллере, повтор cancel раз в секунду только до подтверждения и при раскрытии/остановке. Они не задерживают отправку команды. IO worker журнала существует максимум 5 секунд после записи. Таймер UI 200 мс и диагностические датчики живут только при раскрытой карточке «Датчики» и resumed-активити. UI снимает ShimState listeners в onStop, StateActivity снимает listener в onDestroy. Тестовая кнопка явно планирует снятие через 3 секунды, даже если UI успеет уйти в фон; это однократное завершение ручного теста.

```sh
adb shell dumpsys batterystats --charged dev.pavlov.foldlidshim
adb shell dumpsys meminfo dev.pavlov.foldlidshim
adb shell dumpsys procstats --hours 3 dev.pavlov.foldlidshim
```

Смотреть частоту wakeups, partial wakelocks, работу сенсоров и CPU в batterystats; total PSS, Java/native heap и число потоков в meminfo; длительность foreground/service и min/avg/max PSS/USS в procstats. Сравнивать одинаковые интервалы простоя/складываний после зарядки. Численных результатов без телефона нет.

## Диагноз Холла и что делает костыль

`HallDiagnosis` хранит историю только за текущую сессию службы: минимум и максимум настоящего hinge, последний угол, изменения базового состояния, а если его callback недоступен, текущего состояния без собственного запроса. Override не считается изменением Холла. Hinge наблюдается отдельно от выбранного управляющего источника.

- «работает»: состояние без собственного запроса менялось и сейчас согласуется с углом (0 в закрытой зоне, 2/3 в открытой).
- «залип открыто»: состояние без собственного запроса всегда 2/3, hinge менялся. Закрытие запрашивается по углу, при раскрытии возвращается базовое открытое состояние.
- «залип закрыто»: состояние без собственного запроса всё время 0, получен hinge 0.0 и максимальный угол сессии остался 0.0, прошло хотя бы 60 секунд. Диагноз не блокирует команды; при появлении угла раскрытия действует путь OPENED с выдержкой 700 мс.
- «пока неясно»: данных недостаточно или они не согласуются. Отсутствие событий hinge не приравнивается к нулевому углу.

## Плитка

Добавьте «Экран Fold» через редактирование быстрых настроек. Подпись показывает текущее состояние; при недоступном DeviceStateManager плитка недоступна. Плитка использует текущее состояние DeviceStateCallback и запускает StateActivity только для снятия запроса. Плитка работает и без запущенной службы. STUCK_CLOSED не блокирует автоматические команды службы.

Те же команды доступны кнопками «Открыть принудительно» и «Закрыть принудительно» в карточке «Ручное управление». «Проверить сейчас» сохранилась: закрытие и через три секунды снятие запроса. Это явная ручная проверка.

## Главный экран

Тема `Theme.Material3.DayNight.NoActionBar` поддерживает светлый и тёмный режимы. Карточки с закруглением и отступами 16 dp расположены так:

1. Статус: крупное состояние телефона, угол, диагноз Холла, действие костыля, переключатель службы справа.
2. Ручное управление: принудительные состояния, подсказка о плитке, проверка.
3. Настройки: источник, пороги, ранний запрос, автоподтверждение, показ поверх других приложений, магнитометр, запись датчиков.
4. Датчики: свёрнута по умолчанию, раскрывается по тапу, сырые значения и инверсия осей sub.
5. Шторка уведомлений: пояснение об уведомлении службы.

Для источников `samsung`, `accel`, `hinge` используются `DirectStateController`, `StateActivity` и автоподтверждение через службу специальных возможностей; см. «Как работает переключение». Недоступный выбранный источник не заменяется автоматически. Для accel сохранены инверсия осей и среднее последних пяти пересчётов. Диагностические датчики работают только при раскрытой карточке и resumed-активити, обновление 200 мс.

## Как убрать уведомления из шторки

Приложение не объявляет и не запрашивает POST_NOTIFICATIONS. Обязательное foreground-уведомление создаётся до работы службы на канале IMPORTANCE_MIN, с `setSilent(true)`, без `FOREGROUND_SERVICE_IMMEDIATE`. Отозванное разрешение не является условием запуска службы: `startForeground` вызывается независимо от него. Android требует small icon для foreground-уведомления; убрать её полностью через публичный API нельзя, видимость ограничивается каналом и системным разрешением. Android может показывать службу в системном списке активных приложений.

## Проверки и сборка

Полное описание проверок: [TESTING.md](../TESTING.md).

```sh
./gradlew --no-daemon testDebugUnitTest lintDebug assembleDebug
shellcheck build.sh
```

JUnit: `ConfirmButtonPickerTest` (русские и английские подписи, отсутствие rear display, только отмена, wrapper, пустые кнопки), `DirectPolicyTest` (все ветки выбора команд), `DirectMotionTest`, `HallDiagnosisTest`, тесты порогов, углов, записи датчиков, магнитометра и реплея. Нужны Android SDK 36 и JDK 17. `./build.sh` собирает через Docker APK в `out/app-debug.apk`.

APK ставить (`adb install -r out/app-debug.apk`) только на раскрытом телефоне, когда у службы нет активного запроса CLOSED: `adb shell dumpsys device_state | grep 'Override Request active'` должен показать `false`. Установка убивает процесс, а его запрос остаётся активным от мёртвого pid: новый процесс снять его не может, телефон залипает в CLOSED с выключенным внутренним экраном, в журнале только `device state=0`. Как снять такой запрос, написано в разделе «Остановка и логи». После установки службу поднимает `BootReceiver` по `MY_PACKAGE_REPLACED`, если переключатель был включён; служба спецвозможностей перепривязывается системой сама.

## Остановка и логи

Выключение службы снимает её override. Если процесс был убит (например, установкой APK на закрытом телефоне), запрос остаётся активным от мёртвого pid, и новый процесс снять его не может. `adb shell cmd device_state state reset` тут не помогает: он снимает только запрос самой оболочки. Снять чужой запрос без перезагрузки: `adb shell cmd device_state state 3` (запрос оболочки вытесняет застрявший), затем `adb shell cmd device_state state reset` возвращает физическое состояние; если телефон закрыт, служба через полсекунды сама запрашивает CLOSED заново. Проверка: в `adb shell dumpsys device_state` строка `Override Request active: false` или `Request: mPid=` с pid живого процесса. Логи: `adb logcat -s FoldLidShim`.
